## Interpretación resuelta de `api-summary.json`

El archivo fue generado por `run.ps1` con `k6 run --summary-export`. En este formato heredado, el booleano de `thresholds` contesta si el umbral fue cruzado: `false` significa que **no** fue cruzado y, por tanto, pasó; `true` señala un umbral incumplido. Esto es distinto del nuevo formato de resumen, que expresa el resultado en `thresholds.<name>.ok`. La documentación y explicación de Grafana k6 describen estas formas; véase [opción summary export](https://grafana.com/docs/k6/latest/using-k6/k6-options/reference/#summary-export), [estructura del nuevo resumen](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/#metric-schema) y [aclaración del mantenedor de k6 sobre el booleano heredado](https://community.grafana.com/t/summary-export-command/98472).

La salida concuerda con la consola indicada por el propietario y con el control de salida de `run.ps1`:

- `checks`: 27.520 aprobados, 0 fallidos.
- `http_req_failed.value`: 0.
- El parser de solo lectura encontró 11 entradas de umbral: 0 `true` (cruzadas/incumplidas) y 11 `false` (no cruzadas/aprobadas); no significan “falló”.
- En las métricas `Rate`, `passes`/`fails` cuentan muestras booleanas de la métrica. El script agrega `false` a `api_request_error_rate` cuando una ruta devolvió el estado esperado, y `false` a `server_timing_missing_rate` cuando el encabezado sí pudo medirse. Por ello, `fails = 6.643` en esos Rate no representa solicitudes HTTP fallidas. `value = 0` significa cero muestras verdaderas de error o de tiempo de servidor ausente.
- El umbral agregado de p95 de servidor fue `78.9945 ms` (`p(95)<300`). El p95 de cliente fue `189.776795 ms`; incluye red y no es el p95 de servidor.
- El máximo agregado de servidor fue `2363.94 ms`, un valor extremo que no invalida el umbral p95 pero debe quedar visible al interpretar la distribución.

El perfil midió solo cuatro rutas GET. No contiene una corrida Web (`web-summary.json` no está en el directorio) ni pruebas de rutas autenticadas.

## Correlación del SHA con el despliegue Live

El SHA del archivo de metadatos identifica lo que el runner tenía en su checkout; por sí solo no prueba qué commit servía Render. La última lectura GitHub ya registrada para `staging` mostró ese SHA en la rama alrededor de la ejecución, pero tampoco demuestra qué despliegue estaba `Live`.

Después de `git fetch origin` del 6 de noviembre, `origin/staging` apunta exactamente al SHA medido `ea5604e906ef9345240e1bebaf9f1939e9f9f625`; su fecha de commit es `2026-11-05T17:06:19-05:00`, anterior al inicio de la corrida. La comprobación local confirma que ese SHA es ancestro de la ref obtenida. Esto confirma la referencia Git de Staging, pero no prueba que Render hubiera terminado de desplegarla ni que ese servicio estuviera Live durante la corrida; aún se requiere el recibo/historial de Render.

**Pendiente manual en Render:** en el servicio de Staging, abrir Events/Deploys y registrar, sin capturar secretos:

1. nombre/ID del servicio de Staging;
2. ID del despliegue que estuvo Live durante la corrida;
3. SHA completo del commit de ese despliegue y rama de origen;
4. inicio, finalización y estado Live del despliegue;
5. confirmación de que ningún despliegue distinto reemplazó ese servicio entre `2026-11-05 22:34:25Z` y aproximadamente `22:49Z`.

Comparación requerida: el SHA del despliegue debe coincidir exactamente con `ea5604e906ef9345240e1bebaf9f1939e9f9f625`, y el despliegue debe haber terminado antes de comenzar la carga y permanecer Live durante toda la ventana. Si el SHA difiere o la ventana Live no queda demostrada, esta corrida no se registra como candidato del commit declarado; no se corrige el dato a mano.

La ventana configurada completa fue aproximadamente `22:34:25Z–22:49:00Z`; el escenario `api_load` empezó unos 125 segundos después del inicio y ocupó aproximadamente los últimos 750 segundos. Para la coincidencia más fuerte, Render debe acreditar el SHA durante toda la ventana completa, incluido el calentamiento.

4. Sin cambiar configuración, datos, región ni generador, probar el commit candidato en el servicio aislado equivalente y guardar el segundo run. Si el candidato debe medirse en Staging administrado, confirmar primero que el SHA/ID Live corresponde; preservar la baseline capturada en el entorno equivalente.
5. Documentar el límite residual de equivalencia de instancia/red. Si no se puede mantener infraestructura equivalente, no presentar ambas corridas como una comparación cuantitativa válida.

## Orden de generación/validación de release

Los archivos de gate no se crean hasta completar sus datos. Seguir el orden requerido por los scripts actuales:

1. **HU-STG-01:** completar baseline, correlación de candidato con Render y cuatro filas comparables. Confirmar que el SHA medido sea ancestro del commit que añadirá la evidencia.
2. **HU-STG-03:** producir `docs/release/security-gate-evidence.json` desde datos reales, con `schemaVersion: 1`, `environment: staging`, `baseline` y `candidate`, cuatro rutas únicas e iguales. Incluir fechas UTC, SHA y run ID reales. Validar con `scripts/release/security-gate.ps1 -EvidencePath docs/release/security-gate-evidence.json -ExpectedHeadSha <SHA-HEAD> -RepositoryPath .`. La baseline debe ser anterior a la medición candidata; el SHA candidato debe ser ancestro estricto del HEAD y el archivo no puede declararse completo antes de la captura. Después de medir, solo se permite añadir ese JSON y los dos JSON de metadatos de producción.
3. Verificar en **GitHub Actions** (sin compartir valores de secretos) que `security-gate`, GitGuardian y `QA operational regression` terminaron en `success` sobre los SHAs que exige el validador.
4. **Preparar smoke de Staging:** completar `production-release-candidate.json` desde su plantilla, `schemaVersion: 2`, `deploymentProvider: render-git`, estado `ready-for-smoke` y `sourceCommit` real que ya incluya evidencia de seguridad. El workflow necesita el servicio Render correcto y configura los insumos del smoke. Al enviar ese cambio de metadatos a `staging`, o despachar el workflow desde la ref permitida con SHA/ID reales, obtener el artifact `staging-render-verification` del run exitoso `Staging release smoke`.
5. **HU-MAIN-01:** solo después del smoke exitoso y de contar con una ejecución QA exitosa, completar `production-release-evidence.json` desde su plantilla: versión SemVer, SHA fuente, notas, plan de migración/rollback, IDs de run y SHA QA, run de smoke, SHA/servicio/ID Render y aprobación real con fecha UTC. No escribir contraseñas ni claves.
6. Validar con `scripts/release/validate-production-release.ps1 -EvidencePath docs/release/production-release-evidence.json -ExpectedHeadSha <SHA-HEAD> -ExpectedHeadRef <staging-o-ref-release-permitida> -RepositoryPath .` en el contexto de CI que provee `GITHUB_TOKEN`, `GITHUB_REPOSITORY`, `RENDER_API_KEY` y las variables necesarias. El validador contrasta runs, artifact, checks y despliegue Render real.
7. Solo cuando toda evidencia sea válida, preparar rama/PR para revisión. No hacer merge ni promoción desde esta preparación local.
